# PVD計畫網站 設計文件

- 日期：2026-10-29
- 狀態：等待使用者核可
- 畫面依據：`docs/prototype/index.html`（可點原型，含亮/暗兩種主題；`media/` 為兩支宣傳影片）。本文件描述原型「沒辦法表達」的部分：資料、規則、後端、數據、測試。原型與本文件衝突時，以本文件為準。
- 素材與文案清單：`docs/素材清單.md`

## 1. 這是什麼、為什麼做

PVD計畫是梅拉利卡工作室（Meraklika）和玩家一起決定下一款遊戲的實驗：
- **P = Play**：玩家在網頁上直接試玩 4 款小遊戲原型（每款 5–15 分鐘）。
- **V = Vote**：投票選出最想看到做完的一款。
- **D = Develop**：工作室把勝出的那款做完整，開發過程在開發頁更新，最後上架 Steam。

網站要回答工作室的四個問題（這是數據設計的依據）：
1. 哪些社群平台（Threads、Facebook、巴哈姆特…）值得經營。
2. 各平台的受眾用手機還是電腦。
3. 各平台適合什麼長度的文案（同平台不同貼文要能分開看）。
4. 亮色/暗色主題會不會影響玩家停留在網頁上的時間（AB 測試）。

理想訪客路徑（漏斗）：點社群連結進站 → 玩完 4 款 → 投票 → 留言。

## 2. 目標 / 非目標 / 反目標

**目標**
- 原型中的所有頁面與互動，在電腦與手機上正確運作。
- 真實的匿名留言、投票（含截止與結果）、後台管理。
- 每個訪客固定分到亮或暗主題，並能比較兩組的停留時間。
- 能看出每一條社群連結帶來多少人、什麼裝置、走到漏斗哪一步。

**非目標（這一版不做）**
- 會員/登入（玩家端）。
- 多輪投票的歷史頁（目前只有一輪；資料結構要能容納下一輪，見 §5.3）。
- 開發頁的後台編輯器（開發頁內容改 repo 裡的檔案即可，見 §4.5）。
- 讓目前的 4 款遊戲支援手機（使用者另外處理；網站只要能依每款的設定顯示「僅支援電腦遊玩」）。

**反目標（做到了也算失敗）**
- 投票期間任何人（含網頁原始碼、API 回應）能看到即時票數。後台例外。
- 玩家要登入或填資料才能玩、投、留言。
- 遊戲裡拖曳時整個網頁跟著捲動，或首頁標題與影片銜接時跳一下。
- 費用超出各服務免費額度（網域除外）。

**前端技術由實作者決定**，但需符合：無需建置也能部署的靜態檔，或簡單建置流程；不引入大型框架的必要性需說明。原型是單一 HTML，可直接拆成正式檔案。

## 4. 功能規格

### 4.1 首頁（已定案，照原型）
- 1920×1080 舞台等比縮放；P/V/D 色塊電腦滑過展開、手機兩段式（第一下展開並出現「→ 試玩頁」按鈕）。手機直向改直排置中、展開往兩側長。
- 「PVD計畫是什麼?」從影片 0.8 秒處接播，標題位置與影片畫格一致才不會跳；播完或關閉回到標題。手機直排時先滑回橫排再切影片。
- 亮色組播 `pvd-light.mp4`，暗色組播 `pvd-dark.mp4`。暗色組首頁舞台底色固定 #0f1d33（與暗色影片一致，不套用內容區的炭灰）。
- **影片會再改版（使用者已告知）**：亮/暗、橫/直共 4 支可能都會換新版，換好前先用現有的兩支橫版（手機直拿也先用橫版）。實作要讓換影片只需替換檔案＋改一份設定：檔名、接播秒數、標題在畫格中的位置都放設定檔，不寫死在程式裡。有直版之後，手機直拿改播直版。每次換影片都要重新對一次「標題與影片畫格對齊」。
- 往下捲是介紹區（文案待使用者提供）。

### 4.2 頁首（三個子頁共用）
- 左上：「首頁」按鈕、分隔線、P/V/D 小色塊頁籤（目前頁加黑框）。右上：目前頁標題（色塊+英文字+中文小字；手機省略中文）。
- 投票結束後，V 頁籤右上角掛「End」小標籤（全站）。

### 4.3 試玩頁
- 一屏不捲動顯示 4 款：圖示、名稱、時長、支援裝置圖示（電腦/手機）。
- 電腦：左清單、右詳情（名稱、時長、裝置圖示、介紹、開始試玩、留言板）。預設選第一款。
- 手機：點一款從底部拉出抽屜（約 88% 高），內容同電腦詳情。
- 不支援手機的遊戲，在觸控裝置上「開始試玩」變灰並顯示「僅支援電腦遊玩」。判斷方式：`(hover: none) and (pointer: coarse)`。
- 投票結束後，頁面頂端顯示黃色提醒「投票已結束，但遊戲仍可以試玩」。
- 留言板：見 §4.7。

### 4.4 遊玩頁（WebGame）
- 只有一條上方 bar（「‹ 返回」回試玩頁並選回該款）和 16:9 遊戲畫面。
- 遊戲以 iframe 載入同網站下的 `/games/<遊戲代號>/index.html`。
- 手機直拿：不載入遊戲，只顯示「把手機轉成橫向」提示；轉橫才載入開始。玩到一半轉回直向 → 遊戲暫停並蓋上提示（iframe 保留，不重新載入）。暫停機制見 §6.2。
- 手機橫拿：bar 改左側細條。
- 遊戲區防誤觸：`touch-action: none`、`overscroll-behavior: contain`、禁止選字與長按選單。已知擋不掉：iPhone 邊緣返回手勢。
- 進入遊玩頁即記為「玩過」（存在本機，投票頁顯示用）。

### 4.5 開發頁
- 單欄日誌，可捲動：最後更新日期、標題、目前開發狀況、近期開發目標、工作室 LOGO 與簡介、外部連結（Threads / Facebook / Discord）。
- 內容放在 repo 的一個文字檔（例如 `content/develop.md`），使用者改檔推送即更新。格式由實作者決定，但要讓不寫程式的人能改。

### 4.6 投票頁
- 進行中：左側倒數（電腦一行一個數字；手機橫排）＋截止日「M/D(週) HH:mm 截止」；右側標題「哪一款遊戲你希望開發者繼續做完?」與 4 列選項。每列：圈選、圖示、名稱、「✓ 玩過了」或「還沒玩過 + 去試玩 ›」。
- 規則（使用者已定）：
  - 每人一票，**截止前可改投**（點另一款即改投）。
  - **沒玩過也可以投**。
  - 投票期間**不公開任何票數**（API 也不能回傳）。
  - 投票期約 2–4 週，起訖時間設定在伺服器（台灣時間），前端倒數以伺服器時間校正。
- 結束後（時間到自動切換，不需重新部署）：左側勝出卡（圖示、名稱、票數、占比），右側「最終票數」依名次排列長條。全站進入「已結束」狀態（§4.2、§4.3）。
- 網站上線時第一輪就已開始，不會有「投票還沒開始」的狀態。唯一的空檔是**上一輪結束、下一輪還沒開始**：此時照常顯示上一輪結果（勝出卡＋最終票數），直到後台設定的下一輪開始時間到了才切換成新一輪。
- **同票（使用者已定）**：最高票同票時不自動判定，結果頁先顯示「結果統計中」，由使用者在後台指定勝出的那一款後才顯示勝出卡。
- 「一人」的認定（使用者已同意）：伺服器設定的長效 cookie 隨機編號 + Turnstile + 寬鬆的 IP 頻率限制；不做裝置指紋、不要求登入。換瀏覽器、無痕、App 內建瀏覽器會被當新人，這是已知且接受的限制。

### 4.7 留言板
- 匿名：每則只有小頭像 + 內容，沒有名字。最多 120 字。
- 頭像：8 個可選（目前是程式畫的色塊表情，可換成使用者提供的圖），留言框左側頭像鈕點開，在按鈕正上方跳小彈窗（4×2，不壓黑背景）。預設隨機，選過記在本機。
- 送出後**立即公開**，不審核。新留言排最上面；留言多時留言區可捲動。
- 送出需通過 Turnstile；同一訪客頻率限制（建議值：30 秒 1 則、每小時 20 則，實作者可調）。
- 某款被後台鎖住時：輸入區整塊拿掉，改顯示一行「留言功能暫時無法使用」，既有留言照常顯示。

### 4.8 後台（只有使用者本人）
- 位置：`/admin`，以 Cloudflare Access 限制只有使用者的 email 能進（免寫登入程式；實作者若有更簡單且同等安全的做法可替換，但要說明）。
- 功能：
  1. 依遊戲列出留言（新到舊），可刪除單則（軟刪除即可，前台不再顯示）。
  2. 每款遊戲一個「鎖住留言」開關。
  3. 查看目前票數（只有後台看得到）。
  4. 設定投票起訖時間，以及開新一輪。
  5. 最高票同票時，指定勝出的那一款。
- 不需要漂亮，能用即可。

### 4.9 主題與 AB 測試
- 每位訪客第一次進站時隨機分到亮或暗（各 50%），之後固定（存 cookie / 本機）。不跟系統深色設定。
- 分組由 PostHog 功能旗標（feature flag / experiment）決定，以便日後開新實驗；為避免首屏閃色，實作者可先用本機已存的分組立即套用。
- 暗色主題定案值見原型 `:root.dark` 與 `.db` 區塊：內容區炭灰 #18181d、卡片 #222128、文字 #eeece8、框線 #77737f、品牌色塊維持原色、暗色試玩鈕 #c9403a、黃/綠底上的字固定深色 #2d2144。
- 要回答的問題（使用者已定）：**玩家會不會因為不喜歡某個主題就直接離開**。
- 主要指標：
  1. **很快離開的比例**：進站後 N 秒內（建議 10 秒與 30 秒兩條）就關掉、沒有點任何東西的訪客比例。
  2. **整趟停留時間**：從進站到離開，**所有頁面都算，含遊玩頁**。只算分頁在前景的時間；不要求滑鼠鍵盤有互動，因為網頁偵測不到玩家在遊戲框裡的操作。
- 次要觀察：玩過款數、是否投票、是否留言。

### 4.10 數據與歸因
- 社群連結一律帶 UTM 參數：`utm_source`=平台（threads / facebook / bahamut…）、`utm_campaign`=活動（例如 pvd-round1）、`utm_content`=哪一篇貼文/哪種文案。實作者提供一個簡單的連結產生方式（例如一份說明 + 範例，或後台一個小表單）。
- PostHog 需記錄的事件（名稱可調整）：
  - 進站（含 UTM、裝置類型、主題分組）
  - 播放宣傳影片、看完影片
  - 進入試玩頁、打開某款詳情
  - 開始遊玩某款（進入遊玩頁）、離開遊玩頁（含停留秒數）
  - 投票、改投
  - 送出留言
- 流量預估（使用者提供）：每月最多幾千次瀏覽。Cloudflare 與 PostHog 免費方案都綽綽有餘，事件可以記細一點。
- 漏斗用 PostHog 內建漏斗圖，拆成兩條（我的判斷：留言與投票沒有先後關係）：「進站 → 開始玩任一款 → 投票」與「進站 → 開始玩任一款 → 留言」，完成期限 7 天，可依來源、貼文、裝置、主題分組比較。
- 使用者要能在 PostHog 看到：各來源的人數與裝置比例、各來源走到漏斗每一步的比例、兩種主題的停留時間比較。實作者建好這幾個儀表板。

## 5. 資料與介面（給實作者的方向，細節自行設計）

### 5.1 訪客識別
伺服器在第一次呼叫 API 時設定 `HttpOnly`、`Secure`、`SameSite=Lax`、效期一年的隨機訪客編號 cookie。投票與留言頻率限制都以它為主、IP 為輔。

### 5.2 D1 資料（建議）
- 遊戲設定：代號、是否鎖留言（名稱、介紹等靜態資料可放前端設定檔）。
- 留言：遊戲代號、頭像編號、內容、訪客編號、IP 雜湊、建立時間、是否刪除。
- 投票：輪次、訪客編號、遊戲代號、建立/更新時間（每輪每訪客一筆，改投即更新）。
- 投票輪次：輪次編號、開始、截止。

### 5.3 多輪
這一版只跑第一輪，但投票資料要帶輪次，以後開第二輪不必改資料表。

## 6. 遊戲接入

### 6.1 檔案
每款遊戲是一個靜態資料夾（目前 `E:\Project\Game\WebGame_*` 的 `game/` 都是 `index.html` + js + art + audio，約 1–11MB），放到網站的 `/games/<代號>/`。所有資源路徑必須是相對路徑。

### 6.2 遊戲需要配合的地方
- 在 iframe 裡能正常執行，不改動上層頁面。
- **本機儲存的鍵名照《遊戲接入規範》（`docs/遊戲接入規範.md`）**：4 款遊戲和網站在同一個網址底下，共用同一份瀏覽器儲存空間。
- **網站版不能自動下載試玩紀錄**：目前 4 款遊戲在一局結束時都會把試玩紀錄存成 JSON 檔下載到玩家電腦（開發測試用），網站版必須移除（使用者會在遊戲端移除）。網站不收集遊戲內的試玩紀錄。
- 支援「暫停/繼續」訊息：網站在手機轉回直向、或分頁被切走時，會用 `postMessage` 送 `{type:'pvd:pause'}` / `{type:'pvd:resume'}`。遊戲不支援的話，網站只蓋提示，遊戲會在背後繼續跑（可接受，但體驗較差）。
- （可選）遊戲在玩家完成一局時送 `{type:'pvd:finish'}` 給上層，數據可多記一個「玩完」事件。

### 6.3 遊戲還沒改好時（我的判斷）
實際查過 4 款遊戲（2026-10-29）：鍵名都已各自帶前綴（`bcv19_`、`slimeTetris_v26_`、`gamelog-WebGame_DungeonZoo-`，GhostEchoV2 沒有用本機儲存），彼此不會撞，**不需要部署時注入改鍵名的程式**。之前說 SlimeTetris 會撞是誤判（變數名稱通用，但實際鍵值有前綴）。
階段 1 不等遊戲修改；暫停/繼續在遊戲支援前，只蓋提示不暫停。試玩紀錄下載必須在階段 1 前由使用者在遊戲端移除。

## 7. 分階段實作與測試

每個階段都部署到 Cloudflare 的預覽網址，使用者照該階段的檢查清單在電腦與手機上測過才進下一階段。

| 階段 | 內容 | 使用者要測的重點 |
|---|---|---|
| 1. 靜態網站上線 | 首頁、試玩頁、遊玩頁、開發頁、投票頁畫面（投票與留言先用假資料）；4 款真遊戲接入；亮/暗主題（先用切換鈕） | 各頁在電腦（Chrome/Edge/Safari）、iPhone Safari、Android Chrome、Threads 與 FB 的 App 內瀏覽器都正常；影片銜接；手機轉向提示；遊戲拖曳不捲動頁面 |
| 2. 留言與後台 | 留言 API、Turnstile、頻率限制、頭像；後台登入、刪除、鎖留言 | 在兩台裝置互看留言；連發會被擋；後台刪除後前台消失；鎖住後顯示「留言功能暫時無法使用」 |
| 3. 投票 | 投票 API、改投、伺服器時間倒數、自動結束與結果、全站結束狀態；後台看票數、設起訖 | 用一個 10 分鐘的測試輪：投、改投、換瀏覽器算新人、時間到自動切結果；投票中查不到票數 |
| 4. 數據與 AB | PostHog 事件、UTM、主題分組改由實驗決定（拿掉切換鈕）、三個儀表板 | 用幾條測試連結進站，在 PostHog 看到正確來源、裝置、漏斗；兩種主題都有人被分到 |
| 5. 封測 | 找 10–20 位朋友用自己的手機電腦玩幾天 | 收集問題與數據是否合理；清掉測試資料 |

## 7.1 帳號設定分工（我的判斷）
使用者自己申請 Cloudflare 與 PostHog 帳號，建立一組權限受限的 Cloudflare API token 與 PostHog 專案金鑰交給實作者；之後 D1、Pages 綁定、Turnstile、Access、PostHog 實驗與儀表板都由實作者用指令與 API 建立，並把步驟寫進 repo 的說明文件，換人也能重做。需要使用者在網頁上點的步驟（例如 Access 綁 email）附逐步清單。

## 8. 留給實作者決定
- 前端是否用框架、檔案拆分方式、API 路徑命名。
- 頻率限制的確切數值、Turnstile 的呈現模式（建議隱形模式）。
- 後台畫面樣式。
- PostHog 事件與屬性的確切命名。

## 9. 我（Claude）做的判斷，使用者尚未逐一確認
- 「玩過」= 進入過該款的遊玩頁，存在本機；換瀏覽器就不記得。
- 後台用 Cloudflare Access 登入。
- 後台可以看到投票中的票數。
- AB 停留時間只算分頁在前景的時間；「很快離開」的門檻用 10 秒與 30 秒。

- 頻率限制建議值：30 秒 1 則、每小時 20 則。

- 暫停/繼續需要 4 款遊戲配合修改；鍵名已不衝突，日後新遊戲照《遊戲接入規範》。
